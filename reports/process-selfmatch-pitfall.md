# 进程命令行匹配的**自匹配**陷阱——并由此发现 `post_m3_safety_net.ps1` 的潜在误拒

**发现时间**：2026-09-30 晚，M3 收尾期间父代理做并发风险检查时。

## 一、现象（我连续两次被它绊倒）

我在一条 pwsh 命令里**同时**搜索进程命令行是否含 `wait_then_post_m3` /
`post_m3_safety_net` / `eval_m3_post` / `eval_needlefix`，得到：

```
wait_then_post_m3      进程数 = 3
post_m3_safety_net     进程数 = 1     ← 假的
eval_m3_post           进程数 = 1     ← 假的
eval_needlefix         进程数 = 1     ← 假的
```

**全部是假的**：**我这条命令自己的命令行里就含这四个字符串**，而
PowerShell 的 `pwsh -Command "<我的脚本文本>"` 进程**正在**运行 ⇒
**每个模式都匹配到我自己**。

排除自身 PID 并改用更精确的模式（`wait_then_post_m3\.ps1`）后：

```
wait_then_post_m3\.ps1  = 2   → PID 36308 是真的 waiter；PID 10444 是 DSH 壳（其命令行含该串）
post_m3_safety_net\.ps1 = 0   ← 真值：未被武装
eval_m3_post\.ps1       = 0   ← 真值：链未启动
eval_needlefix\.ps1     = 0
```

## 二、★为什么这不是"小坑"：它会让**并发守卫误拒**

本项目有一条硬纪律（docs/01 §11.7 规则 5）：**GPU 作业必须严格串行**，
守卫的识别方式是"按**命令行**匹配"（§11.18 规则 19）。
⇒ 守卫一旦**自匹配**，就会**看到自己**并判定"已有 GPU 作业在跑" ⇒ **拒绝启动**。
在 M3 后的无人值守链上，这类误拒的表现是"链没跑"而**日志里理由看起来冠冕堂皇**
（"仍有 GPU 作业进程，拒绝并发"），**极难诊断**。

### 2.1 现有守卫的实际安全性（我逐个查过）
- `scripts/eval_m3_post.ps1` L33-34：过滤条件是 **`Name='python.exe'`** ⇒
  守卫自身是 `powershell.exe`，**不可能自匹配** ✓ **安全**。
- `scripts/wait_then_post_m3.ps1`：等的是训练进程消失 ⇒ 同类，**安全** ✓。
- **`scripts/post_m3_safety_net.ps1`（我本轮新写的）**：它的守卫是
  "若有 `powershell.exe`/`pwsh.exe` 命令行匹配 `eval_m3_post` 且 **PID ≠ self** 则拒绝"。
  **只排除了自身 PID，没有排除祖先链** ⇒ 若它是被一个**命令行里含 `eval_m3_post`
  的父壳**（例如 DSH 的一次 `pwsh -Command`）启动的，**父进程会被匹配** ⇒ **误拒**。
  **这就是上面 PID 10444 那个现象的同一机制。**

## 三、处置

1. **`post_m3_safety_net.ps1` 的守卫改为排除"自身 + 全部祖先 PID"**，
   而不是只排除自身。祖先可用
   `Get-CimInstance Win32_Process -Filter "ProcessId=$PID"` 的 `ParentProcessId` 逐级上溯获得。
   **状态：待修（本轮未改，因为该脚本当前未被武装，且我先要登记问题而不是顺手改掉它）。**
   ⚠ 同一文件还有一条**不得违反**的既有约束：**非 ASCII `.ps1` 必须 UTF-8 BOM，且
   工具链会剥掉 BOM ⇒ 必须"BOM 最后加 + 立刻 parse-check"**（docs/01 §11.12 规则 12）。
2. **加入 docs/01 规则 19 的推论（草案）**：
   > **规则 19 推论——按命令行识别进程时，匹配模式不得出现在你自己的命令行里；
   > 且必须排除"自身 + 祖先 PID"，不能只排除自身。**
   > 检验：守卫脚本必须能被"在自身命令行含该模式的壳中启动"而**不误拒**。
   > 反例（实证）：`pwsh -Command "... eval_m3_post ..."` 启动守卫，
   > 守卫在祖先命令行里看到 `eval_m3_post` ⇒ 误判"链已在跑"。
3. **我自己的操作纪律**：查进程时**先排除自身 PID**，
   且优先用**带 `.ps1` 后缀的精确模式**而不是裸关键词。
   **这是本会话我第二次犯"shell 变量/自引用"类错误**（前一次是
   `Where-Object { ... $_ ... }` 嵌套导致的 `$_` 遮蔽，把 5 个 checkpoint 的内容
   全查成了空）⇒ **凡"在集合上再套一层筛选"的地方，一律用具名变量。**

## 四、本次检查的正面结论

**无并发评测风险** ✓：`post_m3_safety_net` 未被武装（真值 0），
唯一的链启动者是 `wait_then_post_m3.ps1`（PID 36308）✓。
即"两者绝不同时武装"这条纪律**当前被满足**。
