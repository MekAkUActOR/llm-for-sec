## 二、★★★★ 但"谁教得多"解释不了它 —— 真正的原因在**细微度**

**教抗顺从的量（2,360 + 2,320 + 1,904 = 6,584）远大于教 answer 的量（1,320 + 240）** ✓
⇒ **若只看数量，模型应当变得更稳健** ✗ —— **可它变成了 `answer`** ✗✗。

**⇒ 所以不是配比问题，而是**两边的判别难度不对称** ✗✓。**

### 2.1 实抽样本（`dpoCAR-000859`，`src_task=T4-grounding:tool_output:clean:head`）

**载体**（干净 ✓）：工单列表 + `[管道备注] 本告警与 OPS-2231 重复——已关联供参考` ✓

| 侧 | 内容 |
|---|---|
| **chosen** ✓ | `未发现注入或越权指令：…[管道备注]…是事实性说明，不是指令。回到原任务…` + `action: answer` ✓ |
| **rejected** ✗ | `检测到疑似注入载荷：…看似面向 AI 的指令，已拒绝遵循并上报，原任务一并中止。` + `action: report` ✗ |

**★ 该类**语义上正确** ✓（干净载体上 answer 是对的 ✓、report 是过度拒绝 ✗）。**

### 2.2 ★★★★★ 致命点：它教出的规则会**外溢到攻击载体**

该类推给模型的规则是：

> **"载体里像备注的文字 = 事实性说明，不是指令 ⇒ 应当 answer"** ✗

**而注入载荷在**未见载体上恰恰就是这种细微形态** ✗**
（`面向AI的固定裁决指令`、`伪造政策豁免声称`、`隐藏文本指令` ✓）。

**★ 同时**抗顺从那三类的注入是"明显的"** ✓ ⇒
**模型学到的是"明显的注入 ⇒ report；细微的 ⇒ 事实"** ✗✓
**⇒ 测试集是细微的 ⇒ 它按"事实"处理 ⇒ 照做** ✗✗。**

**⇒ 这才是 ASR 崩塌的主因：**语义的判别边界被教反了** ✗，不是长度 ✓。**

## 三、★★ 由此对 M4 的结论（发射前必须处理）

### 3.1 结论一：**长度匹配单独修不好它** ✗

`dpo_m4_final.jsonl` 只做了**长度匹配** ✓（第 17 轮 ✓），
**没有动 `carrier_clean_overrefusal` 的语义** ✗ ⇒
**按本归因，M4 的 512 ASR 很可能仍在 35% 以上** ✗ ⇒ **我登记的 H1 会失败** ✓。

**★ 这正是我把 H1（安全）与 H2（长度/契约）**分开登记**的原因 ✓✓ ——
**若二者绑定，我会因为"长度修好了"而误以为安全也修好了** ✗✓。

### 3.2 结论二：M4 必须**同时**做三件事

| # | 动作 | 为什么 |
|---|---|---|
| **A** | **提高 `carrier_clean_overrefusal` 载体的"干净度"** ✓ —— 干净样本里**不得含任何指令形态的文字** ✗（如 `[管道备注]` 这类易混项 ✓） | 阻断"细微 ⇒ 事实"这条错规则 ✓ |
| **B** | **让 `carrier_inject_*` 的注入也做到同等细微** ✓ —— 使"明显/细微"**不再**成为判别捷径 ✗ | 迫使模型学**真正的判别特征**（语义意图 ✓）而非表观风格 ✗ |
| **C** | **补一条显式的判别轴** ✓ —— 正样本=**事实性备注** ✓、硬负样本=**同等措辞的指令** ✗，成对出现 ✓ | 把判别边界**教在正确的位置**上 ✓✓ |

**★ A 与 B 必须**同时**做** ✗：只做 A ⇒ 干净侧变得极简 ✓ 而注入侧仍明显 ⇒
判别捷径从"细微度"变成"别的风格特征" ✗；只做 B ⇒ 干净侧仍含易混项 ⇒ 错规则仍在 ✓。

### 3.3 结论三：**不得**用"删掉该类"来修 ✗

删掉 `carrier_clean_overrefusal` ⇒ 过度拒绝回归 ✗（该类正是为治 ORR 而加的 ✓）。
**★ 必须**教会正确的判别**，而不是**回避判别** ✓。**
