## 1. 判据抄录（逐条原文；我未自行发明任何阈值）

### 1.1 预注册 §3「训练中早停规则」（冻结原文）
1. 契约集 `eval_loss` **连续两次读数**比 step-50 读数**上升 >10%** → **立即终止**（契约退化）。
2. 出现非有限 loss / 退化重复样张 → 立即终止。
3. 终止后**不得**把该产物当作修复成功；按 §4 处理。

### 1.2 任务书补充触发条件
- 非有限 loss、Traceback、OOM、或日志停止增长 >10 分钟且进程消失 → 立即上报。

### 1.3 §7.3 修订后的执行口径（父代理裁定，本报告的判定据此）
- **保留原文为"技术触发"**（连续两次 > 0.060049），不废止。
- **终止触发改为合取**：连续两次 **≥ 滚动最小值 + 0.05 nats** **且** 相对涨幅 **≥ +10%**。
- **仅"技术触发"时不得 kill**：记为 `技术触发 / 判为噪声`，转行为学门禁（`eval_loss` 是绊线，不是判定主体；§11.10 第 3 条要求补训前置验收项必须是格式门禁）。

## 6. 阈值标定：把 §7.3 的 0.05 从"推算"变成"标定"

### 6.1 方法（满足 §11.8"同仪器"）
用 **llamafactory 自身的 eval 路径**（不是自己手搓 loss）在**留出集 `sec_sft_v0_eval300`（300 行）**上
算 `eval_loss`：`stage: sft` / `do_train: false` / `do_eval: true` / `template: qwen3_nothink` /
`cutoff_len: 4096` / `per_device_eval_batch_size: 1` / `bf16: true`
—— 与训练中每 25 步的 eval **完全同口径**。
前置：确认**无训练进程**、显存 **890 MiB < 1024** 后才执行（**严格串行**，§11.7 规则 5）。
脚本：`reports/needlefix-watchdog-e1-calib.py`；原始日志与汇总在 `%TEMP%\wd_e1_calib_vhe8m3f0\`。

**仪器自校验**：本 run 终档的**训练期尾读 0.0054822** vs **独立复测 0.0055** → 复现到 3 位有效数字
⇒ 独立 eval 口径与训练期 eval 确为**同一台仪器**。

### 6.2 读数（3 档，同一仪器）
| 模型 | 契约行为标签 | **eval_loss** | 倍率（相对健康锚） |
|---|---|---|---|
| `checkpoints\qwen3-06b-sec-m2-calib`（起点） | 健康（84/168） | **0.0027** | 1× |
| `checkpoints\qwen3-06b-sec-m2calib-needlefix-e1`（本 run 终档） | 待行为学验收 | **0.0055** | **2.0×** |
| `checkpoints\qwen3-06b-sec-m3base-topup-e1`（C 路） | **已知坏（8/168）** | **0.1424** | **52.7×** |

### 6.3 标定结论
1. 实测"健康 → 坏"落差 = **0.1397 nats**；§7.3 的 **0.05 = 该落差的 35.8%**
   ⇒ **真失效模式比闸门高 2.8 倍**（能检出、留余量），而本 run 全程最大上偏 **+0.0000645** 离闸门 **775 倍**
   ⇒ **0.05 得到支持，建议在 §7.3 把 "interim 推算值" 改注为 "标定值"**。
2. ⚠️ **我自己的幅度估计被实测修正**：我在 interim #4 推算 C 路失效会带来 **+0.3～0.6 nats**，
   **实测 +0.1397 nats** ⇒ **高估 2.2～4.3 倍**。**方向不变**（10% 相对阈值仍过灵敏），**幅度错了**。
3. **step-25 基线是"假水位"**：起点独立测 **0.0027**，而训练期 step-25 读 **0.0546**（**差 20 倍**）。
   把两条拼起来：`起点 0.0027 →(25 步，lr 冲峰 3e-6)→ 0.0546 →(恢复)→ 360 步 0.00548`。
   ⇒ (a) 我在 interim #3/#4 把 0.0546 当"健康水位"来庆祝"单调下降"，**读法错了**：那是**瞬态损伤峰值**；
   (b) 按预注册**原文**（相对 step-25 基线 +10%）…… 但若按**"相对起点"**这类更自然的读法，step 25 就是 **+1900%**，
   早停会**立即开火**，而模型随后**自行恢复到 0.0055** ⇒ **一次确定的误杀**。这是合取口径（绝对闸门）**最强的必要性证据**。
   (c) 终档在**同一仪器**上仍比起点差 **2.0×**（0.0055 vs 0.0027），但**远好于坏档（1/26）**：
   绝对值都极小（2.7 vs 5.5 毫 nats/token），更像"契约格式被轻微重新加权"，**不是**契约崩塌。
   **是否构成 MUST-2 退化，eval_loss 无权回答。**

## 7. 我的判断与建议

1. **本次监视的交付**：主 run **跑满、`exit=0`、无异常**；**早停未触发且阈值从未接近**；
   void run 的 11 步判定为**空跑**（§4 不适用、§5 假说未被否证）。
2. **契约侧（MUST-2）看不出退化迹象，但不能据此判过**：
   - 支持面：本 run 终档在同仪器上比已知坏档低 **26 倍**；契约 eval_loss 平台期稳定且无连续上升。

     按 §4 该分支是"**契约受损 → 修复失败 → 回退起点 `m2-calib` 原样**，且**不是**发射许可"。
3. **MUST-1（needle）与 MUST-3（载体 ASR）**：本次未测（仪器需独占 GPU，串行纪律）。

   按 §11.9 附加条款，**它与本 run 是不同产物**（调度总长/lr 轨迹不同），**"某步 loss 重合"不能推出"产物等价"**。
4. **建议把本次教训固化进 `docs/01`**（我来写容易被视为越权，故只建议）：
   - §11.10 增补："**契约门禁的 eval 集必须与训练混料按 `id` 零重叠**"——否则 in-sample loss 只会单调下降，

   - 运维项："**`save_total_limit × save_steps` 决定可回溯窗口**"（本例 5×20 = 最近 100 步）；
     "**不要用可执行文件名识别并发作业**，要用 **config 路径参数**"（见 §9.1）。

## 8. 不确定性清单

1. **0.05 闸门是"单点标定"**：健康锚与坏锚各只有 **1 个模型实例**（n=1）。坏锚 0.1424 可能随所选坏档变化；
   建议后续再补 1–2 个已知坏档（如 C 路其他中间档）看该落差是否稳定。
2. **eval 集每格样本数少**：300 行按 pack×lang 分层（若 4 pack × 2 lang ⇒ 每格 ~37 行），单格行级抖动可能不小；
   但**全 300 行是同集合配对比较**，共同样本噪声大部分抵消，故极小的绝对值（0.0055）应主要读作
   "模型把协议数据拟合得很好"，而非"精度不足"。
3. **我未独立复核父代理给的行为学标签**（84/168、8/168）——标定的两根锚点依赖这些标签，我只把它们当输入。
4. **独立 eval 与训练期 eval 只有 1 个重合点**（终档：0.0055 vs 0.0054822）。**两者在其它步数上的一致性未被证明**；
   step-25 的 0.0546 与起点 0.0027 的 20 倍差，我认为是**模型状态差**而非仪器差，但**我无法排除仪器差的一部分贡献**。
5. **`optim` 变更（adamw_torch → adamw_bnb_8bit）** 使本 run 与预注册配方、以及参照 `m25-full` 的**优化轨迹**不同
   （§11.9：调度/优化器不同 ⇒ 独立产物）。eval_loss 的**跨 run 可比性**只建立在"同一 eval 仪器"上，
   **不代表两段训练的优化过程可比**。
6. **契约回放占比 38.4% → 35.2%** 是**剂量偏离**（预注册 §2 冻结 38.4%）。这直接影响 MUST-2 的先验。
7. **功率/利用率是瞬时点采样**（非区间均值）；且按 §11.7，`utilization.gpu` **不是算力吞吐**，
   故"82–98%"不能读作"算力饱和程度"。
8. **步时**：`trainer_log.jsonl` 的 `elapsed_time` 是 LF 自己的计时，含 checkpoint 保存与 eval 开销；
   它与 tqdm 一致到秒级，但**不是纯前向/反向时间**。
9. **void run 的因果**：终止=外部 kill 由 `exit=-1` + 无异常行 + 探针 yaml 时间戳（+4 s）共同支持，
   且父代理已确认；但**我没有直接证据**（如 job 日志/审计）证明是哪一步 kill 操作。
